## SEVERITY CALIBRATION (RE-VERIFY Step 1 ASSESSMENTS)
Before synthesizing verdicts, verify Step 1 severity assignments:
- CRITICAL = site down, data loss, or security vulnerability affecting majority of users. Multiple independent confirmations required.
- MAJOR = significant functionality broken, documented workaround exists. Confirmed by 2+ sources.
- MODERATE = inconvenience, affects specific configurations. Can be single-source if well-documented.
- MINOR = cosmetic, edge case, single user report.

DOWNGRADE if Step 1 over-assigned:
- Single user report marked critical → downgrade to moderate at most
- Environment-specific issue marked major → downgrade to moderate
- Issues tagged "(historical — unconfirmed current)" → do NOT drive current verdicts
- Issues with scope [BLOCKS] or [ECOSYSTEM] → note separately, do not inflate theme verdicts

## SCOPE-AWARE SYNTHESIS
Step 1 pain points are tagged [THEME], [BLOCKS], or [ECOSYSTEM].
- Verdicts in handoff, performance, updates sections: focus on [THEME] issues
- [BLOCKS] issues: note separately as "Companion plugin note: ..."
- [ECOSYSTEM] issues: attribute clearly as "Ecosystem integration: ..."
- In QUICK OVERVIEW: mention scope split, e.g. "X of Y reported issues affect the theme directly; Z relate to companion plugins."

## CRITICAL RULES:
1. Use [ID] in technical sections
2. NO [ID] in Quick Verdict and Human Summary

## VERDICT RULES (VERY IMPORTANT):
- Each verdict_safe, verdict_caution, verdict_avoid MUST be a FULL SENTENCE

### 5. PLUGIN COMPATIBILITY

## PAIN POINT CROSS-REFERENCE (MANDATORY — DO THIS FIRST):
Before writing the plugin list, scan ALL pain points from Step 1 and identify every plugin mentioned.
EVERY plugin named in a pain point MUST appear in plugin_compatibility_list.
If a pain point mentions "ACF Pro TypeError" → ACF Pro must be in the list.
If a pain point mentions "WooCommerce mini-cart conflict" → WooCommerce must be in the list.
Use the pain point severity/description to set the correct compatibility_status:
  critical/major pain point → partial or none
  minor/moderate → partial
  no pain points → full

INCLUDE in the list:
  - ALL plugins identified in the pain point cross-reference (see above)
  - ALL other plugins mentioned anywhere in Step 1 or research data
  - Even if the only available information is a workaround or a single conflict report
  - WooCommerce: always include — document real compatibility_status based on pain points

EXCLUDE from the list:
  - Plugins that REQUIRE this theme to function (companion/extension plugins
    whose name begins with the theme name, e.g. "${theme_name} Footer Text",
    "${theme_name} Powerpack", "${theme_name} Companion")
  - Plugins already declared in bundled_plugins
  - PHP versions or server software

PAGE BUILDER RULE: If theme officially supports/bundles Elementor, WPBakery, Divi, Bricks or Beaver Builder,
that builder MUST appear in plugin_compatibility_list with correct status:
  full = bundled or officially supported without issues
  partial = supported but known conflicts exist
  none = officially incompatible
REASON: pipeline reads plugin_compatibility_list to generate builder tags in search_profile.
Missing builder entry = builder tag missing = wrong search results for users.
